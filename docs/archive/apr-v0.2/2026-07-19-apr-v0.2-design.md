# Android Project Runtime v0.2 Design

- Date: 2026-07-19
- Status: Approved
- Original requirement: `APR-Design-v0.2.md`

## 1. Product Goal

APR is an Android deterministic verification tool running on macOS. After a developer or AI Agent completes code changes, APR is responsible for automatically completing the real build, install, launch, user-path replay, assertions, screenshot, log collection, and report generation.

APR's execution and judgment process does not use AI, does not invoke models, and does not rely on visual reasoning. After recording once, the Journey can be invoked at low cost and repeatably by developers, Claude Code, or other Agent CLIs.

APR Journey is a fully self-developed JSON protocol, Recorder, Replay, and assertion engine. It does not reuse, invoke, or be compatible with the official Android CLI Journey. The official Journey is only used as a product positioning comparison: the official Journey targets AI-driven exploratory verification, while APR Journey targets deterministic high-frequency regression.

## 2. v0.2 Scope

Included:

- macOS
- Android Application Gradle project
- A single Emulator or USB Device
- Android CLI and ADB integration
- Explicit Gradle Build
- APR interactive Journey Recorder
- Deterministic Journey Replay
- `click`, `longClick`, `inputText`, `swipe`, `back`, `wait`
- `resourceId`, `text`, `contentDescription` Locator
- Activity before/after state checkpoints
- Activity, Element, Logcat explicit assertions
- Stable waiting based on Layout Diff
- Screenshot, per-step Logcat, and structured report
- Stable CLI contract for humans and AI Agents

Not included:

- AI reasoning inside APR
- Invocation or compatibility with the official Journey
- OCR, visual exploration, DFS
- Android Studio Plugin
- Windows, Linux, CI
- Multi-device concurrency or resident Daemon
- Auto-repair Journey
- Auto-inference of business assertions
- Claude Code Skill or SubAgent integration
- Listening to arbitrary raw touches by the user on the device
- Accessibility companion App

## 3. Technology and Architecture

APR uses Node.js, TypeScript, and ESM, with a "core domain + Ports/Adapters" architecture:

```text
CLI -> Application/Runtime -> Domain <- Ports <- Adapters
```

### 3.1 Module Responsibilities

- `domain/journey`: APR Journey protocol, Action, Locator, Expect, Activity Checkpoint, validation rules, and result models.
- `application/runtime`: orchestrates Build, Run, Replay, Collect, Report; responsible for failure abort and result aggregation.
- `application/recorder`: drives interactive recording, reads Layout, selects targets, executes operations, and generates the Journey.
- `ports`: abstract interfaces for Gradle, Android CLI, ADB, clock, filesystem, process execution, etc.
- `adapters`: real Gradle, Android CLI, and ADB invocations based on Node child processes.
- `interaction`: resolves Locator, converts user actions to ADB operations, and manages annotated-screenshot fallback.
- `collector`: continuously collects Logcat, slices by step, and captures screenshots.
- `report`: generates JSON and text reports and manages run artifacts.
- `cli`: parameter parsing, interactive prompts, progress output, and exit-code mapping; carries no business logic.

Domain and Runtime do not directly call `child_process`. All external capabilities are injected via Ports, so deterministic device-free testing can be done with Fake Adapters.

v0.2 is single-process, single-device, single-Journey sequential execution.

## 4. CLI Contract and Agent Usage Path

APR provides three main entry points:

- `apr doctor`: checks Node, ADB, Android CLI, Gradle project, permissions, and device status.
- `apr record`: interactively executes device operations and generates an APR Journey.
- `apr verify`: executes the complete verification loop and is the stable invocation entry for future Skills or SubAgents.

Journey preparation flow:

```text
apr record
-> APR interactively executes operations
-> generate Journey JSON
-> developer or external AI explicitly supplements business expect
-> Journey validation
-> Journey enters the project repository
```

Post-code-change verification flow:

```text
Agent completes development
-> apr verify
-> Gradle Build
-> Android CLI installs and launches the APK
-> APR Replay
-> deterministic checks and assertions
-> Screenshot + segmented Logcat
-> machine-readable report and exit code
```

The stdout of `apr verify --json` outputs only the final JSON; progress and diagnostics are written to stderr. This way external Agents do not need to parse human logs.

Stable exit codes:

- `0`: verification passed
- `1`: project verification failed
- `2`: configuration or Journey input error
- `3`: tool, permission, or device environment error
- `4`: APR internal error

This phase does not implement Claude Code Skill, nor does APR launch SubAgents. Future integrations only consume the stable CLI and report contracts.

## 5. Project Configuration

The project root uses `apr.config.json`:

```json
{
  "version": 1,
  "build": {
    "task": ":app:assembleDebug"
  },
  "artifact": {
    "target": "app",
    "variant": "debug"
  },
  "run": {
    "packageName": "com.example.app",
    "activity": ".MainActivity"
  },
  "idle": {
    "pollIntervalMs": 200,
    "stablePolls": 2,
    "timeoutMs": 5000
  },
  "artifactsDir": ".apr/runs"
}
```

Rules:

- `packageName` is required; it is not guessed from file names or Activity.
- `activity` supports a fully-qualified class name or a relative class name starting with `.`.
- APR normalizes Package and Activity into a complete Component.
- Package is used for process identification, foreground Activity check, crash identification, related log scoping, and report metadata.
- When the config conflicts with the Android CLI project description or APK info, it fails directly; it does not silently override.
- CLI parameters can temporarily override device, Journey, Package, Activity, and report paths, but do not modify the config file.

## 6. APR Journey

Journey describes user operations along with deterministic recorded state and explicit business expectations.

Example step:

```json
{
  "action": "click",
  "locator": {
    "resourceId": "toolbar_search"
  },
  "activity": {
    "before": "com.example.app.MainActivity",
    "after": "com.example.app.SearchActivity"
  },
  "expect": {
    "type": "element",
    "locator": {
      "resourceId": "search_input"
    },
    "timeoutMs": 3000
  }
}
```

### 6.1 Activity Checkpoint

Recorder automatically records for each step:

- The foreground Activity before executing the operation: `activity.before`
- The foreground Activity after the operation completes and Layout stabilizes: `activity.after`

Replay checks `before` before Locator resolution, and checks `after` after the Action and stable wait. Activity is uniformly normalized to a fully-qualified class name in combination with `packageName` from the config.

Activity Checkpoint is a deterministic baseline directly observed from the device and does not belong to business semantic inference. The `expect` supplemented by a human or external AI is handled separately from it.

### 6.2 Locator

Locator fields are:

1. `resourceId`
2. `text`
3. `contentDescription`

Recorder selects a non-empty and unique Locator by the above priority. Replay reports `LOCATOR_NOT_FOUND` and `LOCATOR_AMBIGUOUS` for zero-hit and multi-hit respectively; it does not guess the target.

When a regular Locator cannot locate, `click` and `longClick` can use `android screen capture --annotate` and `android screen resolve` for explicit degradation. Since `screen resolve` can only resolve `#number` labels in an annotated screenshot, the Journey must explicitly save the label selected by the user during recording:

```json
{
  "fallback": {
    "type": "annotatedLabel",
    "label": "#7"
  }
}
```

Replay does not use visual or AI guessing for labels. Without an explicit `fallback`, a regular Locator failure is a failure; only with an explicit label does it capture a new annotated screenshot and resolve. The report must mark the degradation path, the label, and save the annotated screenshot. Other Actions do not accept coordinate fallback.

### 6.3 Action

- `click`: ADB tap
- `longClick`: ADB swipe with the same start and end point and a duration
- `inputText`: ADB input text, depends on a focused input target
- `swipe`: ADB swipe
- `back`: ADB keyevent
- `wait`: only performs Layout stability detection; fixed sleep is not allowed

### 6.4 Expect

Explicit business assertion types:

- `activity`: foreground Activity match
- `element`: a specified element appears in the Layout
- `logcat`: match a specified tag, level, and pattern within the step time window

Recorder does not infer or auto-generate business `expect`.

## 7. Interactive Recorder

v0.2 uses APR interactive recording and does not listen to arbitrary device touches:

1. Check the environment and launch the target App.
2. Read the current Layout and display interactable elements.
3. The user selects an Action.
4. For Actions that require a target, select the target from the Layout element list.
5. For `click` or `longClick`, the user can view the annotated screenshot and explicitly select a `#number` as an optional degradation label.
6. Read and record `activity.before`.
7. APR immediately executes the operation and waits for Layout to stabilize.
8. Read and record `activity.after`.
9. Only steps that actually executed successfully are added to the in-memory Journey.
10. When the user ends, the Journey JSON is written atomically in one shot, to avoid half-finished artifacts.

## 8. Verify Runtime

1. Load and validate the config and Journey.
2. Run the Gradle Wrapper specified task.
3. Invoke `android describe` to get target and output artifact metadata.
4. Uniquely locate the APK by the target and variant in the config; if the result is not unique, fail; do not guess.
5. Start continuous Logcat collection.
6. Use `android run` to install and launch the built APK.
7. Confirm the Package process, foreground Activity, and initial Layout.
8. Establish the Layout Diff baseline.
9. Execute Journey steps sequentially.
10. Whether success or failure, make a best effort to capture the final screenshot, close Logcat, and generate the report.
11. Generate artifacts in a temporary directory, then atomically move to the official run directory.

### 8.1 Single-Step Execution

Each step:

1. Record monotonic clock `T0`.
2. Check `activity.before`.
3. Resolve Locator.
4. Execute Action.
5. Poll `android layout --diff`.
6. After `stablePolls` consecutive empty Diffs, judge stable.
7. Check `activity.after`.
8. Execute the optional business `expect`.
9. Record `T1` and the step log slice for `[T0, T1]`.

Any step failure immediately stops subsequent steps, to avoid continuing operations on an erroneous page.

### 8.2 Layout Stable Wait

- Establish a full Layout baseline before the Action.
- Poll Diff at `pollIntervalMs` after the Action.
- The number of consecutive empty Diffs is configured by `stablePolls`.
- When `timeoutMs` is reached, return `IDLE_TIMEOUT` and save the last Diff.
- The implementation uses an injectable Clock/Scheduler; neither production nor tests rely on hardcoded sleep.

### 8.3 Logcat Time Slicing

- Start a continuous Logcat stream before Replay.
- Each log entry is associated with the monotonic time at receipt.
- Each step slices from the stream using `T0` and `T1`.
- Logcat assertions only match the tag, level, and pattern within this step's window.
- The complete raw log and per-step logs are both saved to the report directory.

## 9. Failure Semantics

Final run state:

- `passed`: Build, Run, Journey, assertions, and necessary collection all succeeded.
- `failed`: the verified project does not meet requirements.
- `error`: configuration, environment, or APR internal issues prevented verification from completing normally.

Fixed failure categories:

```text
CONFIG_INVALID
ENVIRONMENT_MISSING_TOOL
DEVICE_UNAVAILABLE
BUILD_FAILED
APP_LAUNCH_FAILED
APP_CRASHED
LOCATOR_NOT_FOUND
LOCATOR_AMBIGUOUS
ACTION_FAILED
IDLE_TIMEOUT
ACTIVITY_BEFORE_MISMATCH
ACTIVITY_AFTER_MISMATCH
EXPECT_ACTIVITY_FAILED
EXPECT_ELEMENT_FAILED
EXPECT_LOGCAT_FAILED
COLLECTION_FAILED
INTERNAL_ERROR
```

The original failure is the report's primary failure. If post-failure screenshot, log, or report auxiliary collection fails again, it is only recorded as a secondary error and does not override the primary failure.

## 10. Report and Artifacts

Each run generates a unique `runId`:

```text
.apr/runs/<timestamp>-<journey>-<runId>/
├── report.json
├── summary.txt
├── screenshot.png
├── logcat.txt
└── steps/
    ├── 001-logcat.txt
    ├── 001-layout-diff.json
    └── 001-fallback-annotated.png
```

`report.json` contains:

- Report Schema version, run time, and duration
- Project, Package, Activity, Journey name, and Journey content hash
- Device serial number and tool versions
- Build, Run, Structural, Activity Checkpoint, Explicit Expect, Collection layered results
- Per-step Locator, Action, Idle, Activity, assertion, and log slice results
- Coordinate fallback usage record
- One primary failure and several secondary errors

All artifacts are only saved locally and are not uploaded to external services.

## 11. Engineering Dependencies and Security Boundary

- npm with locked `package-lock.json`
- `commander`: CLI parameter parsing
- `@inquirer/prompts`: interactive Recorder
- `zod`: config, Journey, and report boundary validation
- `vitest`: testing and coverage
- External commands based on Node `child_process`

External commands must support timeout and cancellation. Arguments are passed as argument arrays; shell strings are not concatenated.

## 12. Test Strategy

### 12.1 Domain Unit Tests

Cover Journey Schema, Locator priority and ambiguity, Activity normalization, assertions, failure classification, and exit codes.

### 12.2 Adapter Contract Tests

Use temporary fake commands to verify Gradle, Android CLI, and ADB arguments, output parsing, timeout, non-zero exit codes, and abnormal output.

### 12.3 Runtime Integration Tests

Use Fake Ports to verify complete Build, Run, Replay, Collect, Report, including failure-immediate-abort, Activity before/after checks, log time slicing, and degraded locating.

### 12.4 CLI Black-Box Tests

Run the real APR process to verify stdout/stderr isolation, report artifacts, and exit codes for `doctor`, `record`, `verify --json`.

### 12.5 Real-Device Acceptance Tests

Provide a minimal Android sample project with two Activities, locatable elements, and deterministic business logs. Run an end-to-end Journey when Android CLI and a device are available; normal tests do not depend on a device.

Quality gates:

- `npm test`
- `npm run typecheck`
- `npm run lint`
- `npm run build`
- All key state machines and error branches of Domain and Runtime are fully tested
- Tests must not depend on execution order, real time, or fixed sleep

## 13. v0.2 Completion Criteria

- Can generate a Journey containing Action, Locator, and Activity Checkpoint via the APR interactive Recorder.
- Can explicitly supplement and verify Activity, Element, and Logcat business assertions.
- Can automatically execute Gradle Build and Android CLI Run.
- Can deterministically execute all first-phase Actions via ADB.
- Can stably wait based on Layout Diff, without using fixed sleep.
- Can slice and match Logcat by step.
- Can output Screenshot, raw logs, per-step logs, and layered reports.
- Can be stably invoked by any external AI Agent CLI via `apr verify --json`.
- APR's execution and judgment results do not depend on AI.
